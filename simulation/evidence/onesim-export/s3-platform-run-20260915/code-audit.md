# 玉兰万象生成代码审计

## 审计结论

平台生成的 6 个 Python 文件均通过语法编译检查，行为链也完成 5 次端到端执行；但生成代码存在确定的数据传播缺陷，不能支持八项指标的有效计算。该结论与平台报告中“`case_state.cases` 为空”“第二、三轮记录缺失”“未采集到自定义指标”的现象一致。

## 主要缺陷

### 1. 治理工作流没有输出治理结果

`GovernanceWorkflow.py` 的三个 `ProcessRound` 提示均要求模型只返回 `reasoning`，没有要求返回更新后的 `case_state`。随后事件发送代码把输入的本地 `case_state` 原样转发。因此，应急分流、AI处理、人工审核、派单、反馈和服务匹配只出现在推理文本中，没有写入结构化状态。

证据位置：

- `GovernanceWorkflow.py:119`、`:236`、`:353`：允许的顶层返回键只有 `reasoning`；
- `GovernanceWorkflow.py:144`、`:261`、`:378`：发出的 `case_state` 取自未更新的本地输入。

### 2. 指标容器没有跨三轮稳定传播

第一轮更新动作可生成 `metrics_container`，但第二轮发现后的事件和第二轮更新后的事件没有把指标容器继续携带；`events.py` 中第二轮到第三轮的事件结构也缺少该字段。第三轮只能重新生成一个容器，不能可靠保留第一、二轮记录。

证据位置：

- `NewEmploymentWorker.py:382`：第一轮将模型生成的容器发往第二轮；
- `NewEmploymentWorker.py:505-648`：第二轮更新没有接收、追加并输出 `metrics_container`；
- `events.py:186-212`：第二轮更新到第三轮的事件没有 `metrics_container` 字段；
- `NewEmploymentWorker.py:959`：第三轮再次使用模型临时生成的容器。

### 3. 最终指标没有被代码计算

`MetricRecorder.py` 的提示文本提到指标，但允许的模型返回键仍只有 `reasoning`。终止事件随后把输入 `metrics_container` 原样转发，没有计算或写入八项因变量。这解释了平台报告第 8 节“未采集到自定义指标或量化时序数据”。

证据位置：

- `MetricRecorder.py:98`：允许的返回键只有 `reasoning`；
- `MetricRecorder.py:119`：终止事件仅转发输入容器。

### 4. 平台画像与紧凑版批次设计不一致

平台报告记录了 4 个 `NewEmploymentWorker` 和 4 个 `MetricRecorder` 实例，每次运行只抽取其中一个，而不是一个包含骑手与司机批次的从业者代理。这使单次运行不能计算骑手与司机的参与差距，且报告缺少 `round_replicas`，无法证明 S0—S3使用完全相同的抽样顺序。

## 对最终交付的处理

1. 不伪造或补写玉兰万象缺失的 S3 指标。
2. 将本次运行定位为“平台迁移与数据流风险验证”。
3. 正式量化结论使用仓库内经过配置和输出校验的本地仿真：S0—S3 各 20 次、每次 240 名合成从业者、56 个模拟日。
4. 报告中明确说明两套实现的分工及玉兰运行局限。

## 若后续修复平台版本

应让三个 `ProcessRound` 明确返回更新后的 `case_state`；所有轮间事件携带同一个 `metrics_container` 并只做追加；`FinalizeMetrics` 使用确定性代码从 `records` 计算八项指标，而不是让大模型自由概括。修复后必须重新运行全部 S0—S3，当前 S3 五次运行不并入新结果。
